# V2 project plan — faster local editing and review

Status: Priority 2 implementation on `dev/v2-02-batch-workflow` for owner review, 2026-11-02. The owner stated Priority 1 complete and authorized Priority 2. This plan responds to the private `CRITICAL_EVALUATION_2026-11-02.local.md`; that report stays excluded from Git. Priority 2 implementation and remaining owner acceptance checks are recorded in its report. Priorities 3–4 remain planned.

## Product outcome and boundaries

For roughly 200 selected travel photographs, produce useful, consistent local corrections with little per-photo setup. Keep the original immutable, every output traceable, and publication dependent on explicit human image approval. Make paid or cloud processing optional and separately authorized for each run. No recognition result, suggested recipe, refined prompt, successful job, or batch operation grants image approval.

Measure the owner workflow on a varied 20-photo pilot and a later 200-photo batch: time from import to pending local versions, number of actions outside visual review, correction acceptance rate, failed/overcorrected images, memory and disk use, and full-resolution output quality. A target for the 200-photo workflow is under two hours including visual review; record actual results instead of claiming the target from tests.

## Priority 1 — local corrections that work by default

1. Introduce versioned, non-destructive correction recipes. Store source hash, operation sequence and parameters, auto-analysis version, per-photo recommendation, manual overrides, output hashes, and review events. A recipe is independent of a generative prompt. Show a recommended recipe preselected for each photo, with a one-click preview and an obvious reset.
2. Add conservative automatic exposure/levels, white balance, highlight/shadow adjustment, and optional denoise/sharpening. Add straighten/crop and lens/perspective correction only when the inferred transform is sufficiently reliable; otherwise leave it as a visible suggestion. Avoid clipping, oversaturation, halos, forced crops, and invented content. Record measurements and confidence/reason for each recommendation.
3. Decode the source once for full-resolution deterministic processing, write an immutable full-resolution corrected master, and derive the website JPEG separately from that master. Preserve source orientation and color handling; use high-bit-depth processing where supported. The prohibition on sending the original to a **generative editing** provider remains unchanged. Avoid the current extra lossy JPEG stage in the local path.
4. Default the UI to local correction. Local preview and execution require no compiled/approved text prompt, budget entry, or paid-run checkbox. They still create a distinct pending version, retain a receipt, verify source integrity, and require visual approval before export. Paid generative edits retain prompt approval, cost preview, run authorization, and the publication-derivative input rule.

Acceptance: synthetic tests prove unchanged original hash, exact recipe replay on the same source, separate master/web files, no extra lossy intermediate, safe crop bounds, and no local edit without a receipt. The owner compares varied daylight, night, architecture, people, artwork, and panorama photos at full size and rejects overcorrection. Benchmark memory and time on the actual machine.

Priority 1 uses float32 tonal calculations and an 8-bit RGB PNG master after source decode. It does not yet preserve high-bit-depth source samples through export. Geometry defaults to identity because no reliable horizon or lens-profile estimate is available. The owner pilot must assess whether those limits are acceptable.

## Priority 2 — selection and batch workflow

1. Add contact-sheet selection, named recipes, "apply recipe to selection," per-photo recommendation overrides, and a before-run summary of affected photo IDs, predicted operations, output targets, and skipped items. Local batches may exceed V1's 20-photo paid-run cap, but use bounded workers, cancellation, progress, failure isolation, and resumable receipts.
2. Provide a low-click path: import/prefill, review recommendations in a grid, run local batch, then compare and approve/reject each output. Add approve-and-next and reject-and-next keys. Permit explicit, logged promotion of a new version when a photo already has an approved version; never replace approved bytes silently.
3. For generative work, offer batch compile and batch prompt approval only after a per-photo diff and eligibility preview. A shared instruction/recipe may be applied to a selection, but each photo retains its own prompt snapshot, source/profile hash, allowance, consent, and approval record. No blanket semantic-change consent or automatic image approval. Validate conflicts and policy again for every AI-rewritten or owner-edited prompt at approval time.

Acceptance: test mixed eligible/ineligible selections, partial failures, cancellation, restart, duplicate rejected attempts, stale prompts, and promotion events. A 20-photo owner pilot should require no per-photo prompt actions for local corrections; record actual click count and time.

## Priority 3 — local understanding and optional prompt refinement

1. Extend the existing pinned CLIP recognition pipeline for more useful subject/condition candidates and search. Keep tags and editorial labels as suggestions. An exact landmark or location must be owner-confirmed; image appearance never overrides private GPS or owner metadata.
2. Evaluate a separate local vision-language or language model for a short scene description, technical correction proposal, and pre-prompt. CLIP alone cannot generate prose. Choose a model only after verifying license, Windows/Linux CPU viability, download size, memory, latency, model-file hashes, and quality on the owner pilot. Download into the existing ignored, verified model cache; use the canonical `.venv` and locked dependencies.
3. Add an optional prompt-refinement step: deterministic local prompt plus structured owner instructions/constraints -> local text model or OpenAI text model -> editable, immutable AI proposal -> explicit prompt approval -> separately authorized image edit. Record model/template/settings, source/profile identities, input/output, usage, and cost. Cloud text/image analysis is opt-in with a cost preview. If image context is used, send only the metadata-free publication derivative after current-run authorization.
4. Compare the refined prompt with the deterministic baseline on a small owner-reviewed set. Prefer precise requested changes and explicit preservation constraints over length. A model must not invent scene facts, relax approved constraints, expand semantic allowance, or authorize itself. On failure, keep the local prompt available.

Acceptance: mocked providers prove no unexpected network requests, source-photo upload, silent consent, stale approval, or execution. Owner evaluation records prompt usefulness and image fidelity, rather than treating longer prompts as inherently better. Official OpenAI prompting and structured-output guidance: <https://developers.openai.com/api/docs/guides/image-prompting>, <https://developers.openai.com/api/docs/guides/structured-outputs>.

## Priority 4 — accounting, provenance, and cross-platform launch

1. Repair cost reporting. The current Images adapter retains usage but returns `actual_cost_usd=None`; the API does not supply an invoice amount. Store response usage and request identity, compute a **usage-based cost calculation** from a versioned price table and model/settings at the time of the call, and label it calculated. Preserve planning estimate separately. Reconcile with provider billing when an owner-supplied billing export is available; label reconciled amounts and keep unknowns unknown. Include prompt-refinement and paid-analysis calls. Never present a planning amount as a hard provider spending cap. Reference: <https://developers.openai.com/api/docs/guides/image-generation>.
2. Make an optional C2PA-signed publication copy from each approved export image. Record the approved version as an ingredient, the actual deterministic/generative operations, and the signer identity without leaking private GPS, source path, or hidden prompt text. Signing changes the exported file's bytes: retain the approved JPEG and its hash, give the signed copy its own hash/manifest field, and validate the signed asset. Decide certificate/key storage and trust policy before enabling the feature; a signature proves integrity and signer claims, not that the depicted scene is true. Reference: <https://opensource.contentauthenticity.org/docs/getting-started/>.
3. Add a Linux one-command launcher using the same locked `.venv` setup and app configuration. Both platforms must support offline loopback start; LAN binding remains explicit and protected. Avoid rebuilding the frontend when its versioned production bundle is already current. Test fresh install, offline restart with verified local model cache, LAN access control, and recovery on both OSes in CI and owner smoke tests.

Acceptance: mock usage calculations and billing reconciliation are independently testable; unknown actual charges stay visibly unknown. C2PA verification succeeds on exported copies and fails after tampering, while approved bytes remain unchanged. Windows and Linux fresh-clone launch tests run without paid calls or private photos.

## Later candidates, subject to evidence

Local inpainting for bounded people/object removal, RAW/HEIC ingestion, and packaging for users without a Python/Node toolchain merit separate feasibility decisions. Local inpainting remains generative: it receives only the publication derivative, keeps mask limitations visible, creates a pending immutable attempt, and needs explicit semantic-change consent where applicable. Do not add these to the default local correction path without a visual pilot and reproducible model/runtime plan.

## Delivery sequence and gates

Use dedicated V2 branches in this order: `dev/v2-01-local-pipeline`, `dev/v2-02-batch-workflow`, `dev/v2-03-intelligence-prompts`, and `dev/v2-04-provenance-launch`. A small cost-accounting fix may be isolated earlier if the owner wants paid calls before V2's last milestone. Each branch updates the schema, dependency lock/setup, tests, UI guidance, decision log, and technical report as applicable. Use synthetic fixtures and mocked providers in CI; conduct the 20-photo owner pilot before a 200-photo batch. Phase acceptance is based on measured usability and visual quality as well as software tests. The owner reviews each branch before the next implementation phase, merge, or release.
